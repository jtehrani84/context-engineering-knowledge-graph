The Memory System Hit a Wall

The 5-layer architecture from Part 1 worked. Claude remembered across sessions, loaded wiki pages on demand, and applied rules consistently. But after 6 months of daily use, the system had a scaling problem.

128+
Memory Files

The flat MEMORY.md index hit 222 lines. The budget is 200. Every new memory pushed an old one off the edge.

63
Wiki Pages

Every new wiki page required a manual routing table update in CLAUDE.md. Miss it, and Claude never finds the page.

3
Files Surfaced

Session startup showed the 3 most recently modified files. Recent doesn't mean relevant. Working on slides? Here's yesterday's deployment fix.

The Core Issue

Every layer of the system had its own relevance mechanism. Memory used modification time. Wiki used a hand-maintained routing table. Rules loaded everything regardless. They were stacked but not connected.

The question "what should Claude load for this task?" was answered by three independent systems that didn't talk to each other. The answer was always incomplete.

Files Become Nodes. Concepts Become Edges.

A knowledge graph connects the three systems into one traversable structure. Instead of "show me recent files," the session asks "what entities are relevant to this work, and which files discuss them?"

Five Edge Types Connect Everything

REFERENCES

A file mentions an entity. pitch-craft.md → REFERENCES → "slide generation"

APPLIES_TO

A wiki page serves a work context. security-governance.md → APPLIES_TO → "Apex development"

RELATES_TO

Two files share 3+ entities (IDF-filtered). pitch-craft.md → RELATES_TO → slide-visual-design.md

DISCUSSED_IN

An entity appears in a memory file. "Agentforce" → DISCUSSED_IN → agent-harness-project.md

PART_OF

An entity belongs to a project. "AIP" → PART_OF → "Meridian Platform"

Three Phases, One Afternoon

The entire system — graph construction, session integration, and auto-indexing — was built in a single session. Local SQLite. No cloud infrastructure. No API calls. Just entity extraction and traversal.

1

Graph Bootstrap

COMPLETE

Entity-extract every memory, wiki, and rules file. Seed 68 entities across 6 types (accounts, products, projects, systems, concepts). Parse the CLAUDE.md routing table into APPLIES_TO edges. Scan all files for entity mentions. Compute RELATES_TO relationships between files sharing 3+ non-stop-word entities.

# Build the graph
$ bun run build-context-graph.ts
# Output: graph.sqlite
# 377 nodes, 5,102 edges
# Rebuilt from scratch in ~2 seconds
2

Session-Init Integration

COMPLETE

The SessionStart hook queries the graph instead of the hardcoded routing table. It extracts signals from git state (changed files, recent commits, branch name), matches them to entity nodes, and traverses APPLIES_TO (weighted 3x) and REFERENCES edges to find the most relevant wiki and memory files.

# Signal gathering (automatic on every session start)
git diff → file paths → entity matches
git log → commit words → entity matches
cwd → directory names → entity matches
# Traversal
matched entities → APPLIES_TO (3x) + REFERENCES (1x)
→ ranked wiki pages + memory files
# Fallback: if graph.sqlite missing, use old routing
3

Auto-Indexing

COMPLETE

A PostToolUse hook fires on every Write or Edit to a memory, wiki, or rules file. It incrementally updates that file's node and re-scans for entity mentions — no full rebuild needed. The graph stays current as files change, files are created, or files are deleted.

# Triggered automatically on every file write
1. Upsert file node
2. Delete old REFERENCES edges
3. Re-scan for entity mentions
4. Recompute RELATES_TO (IDF-filtered)
# Performance: 61ms per file

Two Quality Problems, Two Fixes

False Positive: "Exa" Matched "Example"

The entity "Exa" (a search API) was matching "example", "exactly", "examination" — appearing in 91 out of 308 files. 30% of the corpus.

Before: substring match
Fix: word-boundary regex for terms under 5 characters
91 → 19 references

Edge Explosion: 16,274 RELATES_TO

High-frequency entities (AIP in 44%, Agentforce in 42%, Slack in 35%) caused nearly every file to relate to every other file. The graph was fully connected — useless for ranking.

Before: 16,274 edges, 2+ shared entities
Fix: IDF stop-word filter (>25%) + raise threshold to 3
16,274 → 2,877 edges (82% reduction)

Under the Hood

The entire system is local. No cloud database, no API calls, no network. SQLite running on your laptop with a TypeScript build script and Python hooks.

Schema (complete)

CREATE TABLE
nodes (id, node_type, name, canonical_name, file_path, properties, created_at, updated_at)
-- UNIQUE(node_type, canonical_name)
CREATE TABLE
edges (id, source_id, target_id, edge_type, confidence, properties, created_at)
-- UNIQUE(source_id, target_id, edge_type)
-- FK with ON DELETE CASCADE
Two tables. Five indexes. That's the whole thing.

What's Left on the Table

The graph currently powers session startup. Three extensions would make it conversational.

FUTURE

Post-First-Message Re-Query

Session-init runs before the user types, so it can't know intent. A second graph query after the first message would load topic-specific context mid-conversation. Requires Claude Code to support deferred context injection.

FUTURE

Graph-Enriched MCP Results

When a CRM query returns "Starbucks owns Service Cloud," the graph could inject related memory — prior analysis notes, feedback on data sources, relevant wiki pages. Tool results would arrive with structural context, not raw data.

FUTURE

Task-Specific Rule Loading

Instead of loading all 11 rules files every session, the graph could identify which rules apply to the current task. Working on slides? Skip the Apex security rules. Working on deployment? Skip the UI design rules. Estimated 40% context savings.

The Memory System Hit a Wall

The 5-layer architecture from Part 1 worked... Claude remembered across sessions, loaded wiki pages on demand, and applied rules consistently. But after six months of daily use it ran into a scaling problem the original design was never built to handle, and I didn't see it coming until the context started feeling noisy.

By then I had 217 memory files, and the flat MEMORY.md index had swollen to 222 lines against a 200-line budget, so every new memory quietly pushed an older one off the bottom. The wiki was at 86 pages, and every one I added meant a manual routing-table edit in CLAUDE.md. If you forgot the edit, Claude simply never found the page. On top of that, session startup surfaced the 3 most recently modified files, but recent and relevant aren't the same thing, and you could be deep in a slide deck and still get handed yesterday's deployment fix.

What was really going on is that every layer had its own idea of relevance. Memory ranked by modification time, the wiki leaned on a hand-maintained routing table, and the rules loaded everything regardless, so I had three mechanisms stacked on top of each other that were never actually connected. The question underneath all of it was always "what should Claude load for this task?", and three independent systems kept answering it without comparing notes, which is why the answer they assembled between them came out incomplete just about every time.

Turning Files and Entities Into a Graph

A knowledge graph ties those three systems into one structure you can actually traverse, so instead of asking "show me recent files," the session asks "which entities matter to this work, and which files discuss them?"

The files themselves are nodes, about 130 memory files, 65 wiki pages, and 11 rules files. So are the entities they talk about (12 accounts, 13 products, 10 systems), and so are the 25 concepts and 9 projects, which puts the whole graph at 379 nodes.

Five Edge Types Connect Everything

Edge Meaning and example
REFERENCESA file mentions an entity. pitch-craft.md → REFERENCES → "slide generation"
APPLIES_TOA wiki page serves a work context. security-governance.md → APPLIES_TO → "Apex development"
RELATES_TOTwo files share 3+ entities (IDF-filtered). pitch-craft.md → RELATES_TO → slide-visual-design.md
DISCUSSED_INAn entity appears in a memory file. "Agentforce" → DISCUSSED_IN → agent-harness-project.md
PART_OFAn entity belongs to a project. "AIP" → PART_OF → "Meridian Platform"

Four Phases, All Shipped

Across two sessions I built the whole thing... graph construction, session integration, auto-indexing, and live tool enrichment. It all runs on local SQLite without any cloud infrastructure or API calls behind it, just entity extraction and traversal, which is the part I like most about it.

1

Graph Bootstrap

First I entity-extract every memory, wiki, and rules file, then seed 68 entities across 6 types (accounts, products, projects, systems, concepts). From there the CLAUDE.md routing table gets parsed into APPLIES_TO edges, every file is scanned for entity mentions, and RELATES_TO relationships are computed between any two files that share 3+ non-stop-word entities.

# Build the graph
$ bun run build-context-graph.ts
# Output: graph.sqlite
# 379 nodes, 5,120 edges
# Rebuilt from scratch in ~2 seconds

Phase 2: Session-Init Integration

With the graph built, the SessionStart hook could query it instead of the hardcoded routing table. It pulls signals out of git state (changed files, recent commits, branch name) and the working directory, matches them to entity nodes, and traverses APPLIES_TO (weighted 3x) and REFERENCES edges to rank the wiki and memory files that matter. If graph.sqlite is missing, it falls back to the old routing.

# Signal gathering (automatic on every session start)
git diff → file paths → entity matches
git log → commit words → entity matches
cwd → directory names → entity matches
# Traversal
matched entities → APPLIES_TO (3x) + REFERENCES (1x)
→ ranked wiki pages + memory files
# Fallback: if graph.sqlite missing, use old routing

Phase 3: Auto-Indexing

To keep the graph current, a PostToolUse hook fires on every Write or Edit to a memory, wiki, or rules file. It upserts that file's node, deletes its old REFERENCES edges, re-scans it for entity mentions, and recomputes RELATES_TO with the IDF filter, all in 61ms per file, which means there's no full rebuild and the graph keeps up as files change, get created, or get deleted.

4

Live Tool Enrichment

The last phase took the graph out of session startup and into the middle of the work. A second PostToolUse hook fires on every MCP tool call to the Salesforce server, pulls entity signals out of the tool input (account names, search queries, SOQL strings), queries the graph for matches, and surfaces the related memory and wiki files right alongside the tool results.

# Triggered on every Salesforce MCP tool call
crm_assets("Acme")
→ extract signals: ["acme"]
→ match entities → traverse edges
→ inject: 3 memory files + 2 wiki pages
# Performance: 55ms per tool call

Two Bugs From the First Build

Both bugs showed up the same way, as a graph that connected far more than it should have. The first was a false positive, where the entity "Exa" (a search API) was substring-matching "example," "exactly," and "examination," so it turned up in 91 out of 308 files, close to a third of the whole corpus. Switching to a word-boundary regex for terms under 5 characters took it from 91 references down to 19.

The second was an edge explosion. A handful of high-frequency entities (AIP in 44% of files, Agentforce in 42%, Slack in 35%) made nearly every file relate to every other one, and with the threshold at 2+ shared entities I ended up with 16,274 RELATES_TO edges, which made the graph fully connected and useless for ranking. I added an IDF stop-word filter (>25%) and raised the threshold to 3, and that brought it down to 2,877 edges, an 82% reduction.

Under the Hood

The entire system is local... SQLite running on your laptop, driven by a TypeScript build script and a handful of Python hooks, with no cloud database, no API calls, and no network anywhere in the loop.

What Was Live and What Got Parked

By the end of the build the graph ran both session startup and live tool enrichment, and I had two extensions left that were waiting on the platform.

LIVE

Graph-Enriched MCP Results

When a CRM query returns data about an account, the graph injects the related context automatically. Ask about Acme and Claude sees the prior analysis notes, the relevant feedback, and the wiki pages sitting right alongside the raw data, because a PostToolUse hook extracts entity signals from the tool input, queries the graph, and surfaces the top 5 related files in 55ms.

The first extension I parked was a re-query after the first message. Session-init runs before the user types, so it can't know intent, and a second graph query once you've said what you're working on would load topic-specific context mid-conversation. When I built this, Claude Code didn't have a PostUserMessage hook type, so there was nothing for that second query to hang off of.

The other one is task-specific rule loading. All 11 rules files loaded every session, and the graph could have worked out which rules actually apply to the task at hand, but Claude Code loaded every rule before any hook ran, so I parked it until the platform could load rules conditionally.
